# CueFlow

CueFlow describes message constraints in CUE and communication order as a server-local finite state machine. The first compiler prototype loads CUE through the official Go API and generates Rust server/client Typestate interfaces.

## Commands

Check a CUE package:

```sh
go run ./cmd/cueflow check --input ./cue/examples
```

Generate a Rust module:

```sh
go run ./cmd/cueflow generate rust --input ./cue/examples --output ./generated/cueflow.rs
```

The `send` and `recv` transitions are interpreted from the server's point of view. The client API is generated by swapping those directions. Every nonterminal state exposes `close()` to send Close and `recv_close()` to wait for the peer's Close. A business receive method can also return `ReceiveOutcome::Closed`; transport failures remain `ProtocolError::Transport`. States with no business transitions are terminal.

Optional CUE fields are represented as `Option<T>`. The generated Serde deserializer accepts a missing field but rejects an explicit `null`, matching CUE's optional-field semantics.

## First version limits

The Rust generator supports object messages with string and boolean fields, plus bounded integer fields that fit `i64`. String validation currently supports non-empty constraints, CUE regular-expression patterns, and length bounds. Integer validation supports inclusive minimum and maximum bounds. A pattern that CUE accepts but the Rust regex crate cannot compile becomes a validation error. `cueflow check` validates protocol semantics independently of any language backend; unsupported CUE/JSON Schema constraints fail Rust generation instead of being silently dropped.

Generated code depends on Serde with its derive feature and the Rust `regex` crate. It defines an async `Transport` trait but does not implement a transport, wire encoding, buffering, backpressure, or Runtime. The selected binary wire format remains open.
