# CueFlow Diary 0005：生成轴与通信边界

日期：2026-11-14

## 1. 不定义通用消息外包装

CueFlow 不定义通用 Envelope，也不要求消息带有 CueFlow 专属的 `message_id`、`tracing_id`、`session_id` 或 `payload` 包装层。

- 业务消息及其元信息由用户在 CUE 中定义；CueFlow 对这些字段保持透明。
- 链路追踪等已有机制优先沿用相关标准和所选传输设施，不由 CueFlow 重复发明。
- 只有在具体协议或所选组合确实需要额外线上信息时，才由用户协议或该组合的既有约定定义；不把某一种做法提升为所有协议的通用规则。

## 2. 组合轴及职责

代码生成按彼此独立的选择组合，而不是为每种组合建立单独方案：

- **Runtime**：语言生态中的异步执行、调度和生命周期设施。
- **Transport**：连接与消息交付方式，例如 WebSocket。
- **Codec**：用户消息数据的编码与解码，例如 JSON。
- **Endpoint**：选择生成客户端、服务端或两者；这是代码生成目标选择，不改变线上协议。

CUE 和 FSM 继续定义业务数据约束、消息方向和状态转移。生成器负责把协议语义映射到所选设施。每个后端只实现明确支持的组合；不支持的组合应给出清楚错误，无须实现完整的笛卡尔积。

## 3. 当前 Runtime 选择

为减少第一阶段的选择成本，先为现有语言后端各选一种常用 Runtime：

- Rust：Tokio。
- Python：`asyncio`。

该决定只限定当前实现与示例，不构成协议语义，也不妨碍未来按实际需求增加其他 Runtime。

## 4. WebSocket + JSON 实验边界

当前实验组合为 Rust/Tokio 与 Python/`asyncio`，使用 WebSocket 传输和 JSON 编码，支持生成客户端、服务端或两端。线上 JSON 直接表示 CUE 定义的业务消息，不额外套 CueFlow Envelope 或消息类型字段；当前状态若只能接收一种消息，FSM 上下文已能确定预期类型。若未来需要在同一状态区分多个消息类型，应依据具体协议选择表达方式，而不是默认添加全局包装。

本实验按一个 CueFlow Session 对应一条 WebSocket 连接处理，不提供连接多路复用。此绑定将协议 Close 映射为 WebSocket 的物理关闭；这是该实验的绑定选择，不是 CueFlow 对所有 Runtime 和 Transport 的要求。若未来协议要求逻辑 Session 结束而底层连接继续使用，应通过用户定义的协议消息或适合的绑定表达该语义。

## 5. 阶段结论

CueFlow 定义协议并生成与目标语言生态衔接的强类型接口；它不另立通用线上元数据标准。先验证少量明确支持的轴组合，遇到需求后再扩展各轴及其兼容关系。
