# CueFlow Diary 0004：编译边界与 Rust 实现路线

日期：2026-10-24

## 1. 项目定位

CueFlow 是基于 CUE 描述通信协议并生成强类型接口的编译工具。CUE 定义消息数据和取值约束，FSM 定义合法的通信时序。生成的 API 应尽可能让非法消息类型和非法状态调用在编译期暴露。

CueFlow 负责协议形式、约束和编排，不重新实现序列化框架、异步运行时或网络协议栈。优先复用各语言生态的成熟设施。

本篇收敛第一阶段的编译边界，并更新此前的两项决定：

- Diary 0002 和 Diary 0003 曾把 Canonical Protocol IR 作为既定 compiler 架构。本篇调整为以 CUE 作为规范协议表示；compiler 可以使用辅助数据结构，但暂不建立第二套规范化协议语义。未来若多后端或代码生成证明确有需要，再评估是否引入独立 IR。
- Diary 0003 曾规定 Close 只能在显式声明 `close: true` 的状态发生。本篇将其改为所有非终止状态都隐式允许 Close，因此 `#State` 不再包含 `close` 字段。

## 2. 协议模型

### CUE 是规范描述

- 使用标准 CUE 语法，不添加 CueFlow 专属关键字。
- `#Protocol` 定义 `messages`、`initial` 和 `states`。
- `messages` 显式把协议 MessageID 关联到 CUE 数据约束。
- `send`、`recv` 描述状态转移；CueFlow compiler 检查消息引用、状态引用和 FSM 语义。
- CUE 约束消息值；CueFlow 定义消息何时、以何种方向出现。

### 以服务端为主语

协议统一以服务端为主语：

- `send` 表示服务端向客户端发送。
- `recv` 表示服务端从客户端接收。
- 客户端协议由 compiler 自动生成对偶，交换 `send` 与 `recv`。

该约定不增加 schema 字段，但要求协议示例使用服务端视角。

### 隐式 Close

所有非终止状态都隐式允许无载荷的 Close 转移：

```text
state --Close--> Terminal
```

用户不必声明 Close，`#State` 也没有 `close` 字段。终止状态没有后续业务转移。Close 表示逻辑 Session 结束，不定义底层连接是否关闭；未完成业务、缓冲区、任务取消、确认和资源释放由具体 Runtime 决定。

### 默认异步

协议采用异步通信模型。发送不代表等待对端处理；双方维护各自的局部 FSM 状态，合法的异步交错不是传输错误。消息交付、缓冲、背压、调度以及 FIFO 等执行保证由 Runtime 实现。

异步不自动提供请求—响应关联。当前 FSM 不推导请求 ID、响应匹配关系或业务因果约束，也不引入计数器、任意 Guard、跨消息业务判断或复杂并发会话模型。

第一阶段保证协议安全性：消息类型和方向符合当前状态所允许的转移。它不保证无死锁、请求最终获得响应、Session 最终关闭，也不证明任意并发交错安全。

## 3. Rust 代码生成

第一阶段优先生成 Rust：

1. 消息对应的 Rust 数据类型。
2. CUE 取值约束所需的运行期校验。
3. 服务端 Typestate API。
4. 自动对偶的客户端 Typestate API。

Typestate 应让错误状态下不可用的方法无法通过 Rust 编译。编译期保证类型和 API 调用顺序；无法编码进 Rust 静态类型的 CUE 约束仍需运行期校验。例如 Serde 能把字节解码为 `String`，但 DNA 字符串的正则约束仍需额外验证。

## 4. 序列化与 Runtime 边界

不自研二进制序列化算法。Rust 生成代码优先复用 Serde 生态；Postcard、CBOR 等是候选，但当前不冻结 Wire Format。Serde 是序列化抽象，不是线上编码协议。各语言可使用不同库，但通信双方必须采用兼容的线上约定。第一版不承诺跨协议版本的二进制兼容性；长期需要考虑稳定字段编号和协议演进。

Runtime 负责消息收发、编解码、缓冲、背压、异步调度、Session 生命周期、网络异常和资源管理。Rust Runtime 可以采用 Tokio，但 Tokio 不属于协议语义。早期生成代码可由 Mock Transport 验证，无须先实现完整网络栈。

## 5. 跨语言方向

目标是统一协议语义，并允许后端采用各语言自然的实现：Rust 可用 Typestate、Serde 和 Tokio；Go 可用结构体与原生并发机制；Python 可用类型注解、数据模型和 asyncio；TypeScript 可用联合类型、泛型和 Promise。这些是未来方向，不是当前多后端交付承诺。AI 可以辅助维护生成器，但正确性仍须通过目标语言编译、测试和协议一致性验证。

## 6. 近期路线

停止扩张协议模型，优先验证最小编译链路：

1. `cueflow check`：加载 CUE，检查协议结构、FSM 以及状态和消息引用。
2. `cueflow generate rust`：生成 Rust 消息类型、约束校验和服务端/客户端 Typestate API。
3. 验证合法时序可编译、非法时序不可编译。
4. 复用 Serde 生态完成消息编解码验证，不预设完整 Wire Format。
5. 用 Mock Transport 验证客户端和服务端的对偶行为。

暂不开发完整 Tokio Runtime、自定义二进制格式、Session 多路复用、自动请求—响应关联、多语言后端、全局死锁自由证明或任意并发交错的完整安全性证明。出现明确需求后再评估。

## 7. 阶段性结论

CueFlow 的核心价值是把消息数据约束与通信时序统一描述，并生成目标语言自然、可靠的强类型接口。只实现必须由 CueFlow 解决的部分，其余复用成熟生态。

当前 schema 足以开始第一版 Rust 编译器原型。下一步应通过 `cueflow check` 和 Rust 代码生成验证设计，而不是继续增加协议抽象。
